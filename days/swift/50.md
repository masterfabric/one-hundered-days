# Day 50: Networking (I) - Error Handling & Loading States

## 📝 Today's Tasks

1.  **Model a Load State:** Use an enum (`idle`/`loading`/`loaded`/`failed`) for the screen's state.
2.  **Render Each State:** Switch on the state to show a spinner, content, or an error view.
3.  **Add Retry:** Offer a retry action on failure.
4.  **Show Empty States:** Handle the successful-but-empty case with `ContentUnavailableView`.

## 📖 Task Explanations

Model the screen's state as one enum: `idle`, `loading`, `loaded(Items)`, `failed(Error)`. The point is that it makes contradictory states unrepresentable — you cannot be loading and failed at the same time, which is exactly the bug that three separate boolean properties produce. Hold it in your view model as a single published property.

Then render each case with a `switch` in the body. Loading gets a `ProgressView`, loaded gets the content, failed gets a message. Because the switch must be exhaustive, adding a new state forces you to design its UI rather than forgetting it — the compiler becomes your checklist for states you'd otherwise discover in production.

Failure needs a way out. Show what went wrong in plain language and put a Retry button next to it that re-runs the same load. Distinguish the cases where retrying could plausibly help (timeout, offline) from those where it can't (404, unauthorized), because a retry button that always fails is worse than an honest message telling the user what to do instead.

Finally, handle success-but-empty, which is a different state from both loading and failure. `ContentUnavailableView` is built for it — a title, a symbol, and an optional description — and `ContentUnavailableView.search` covers the "no results" case for free. An empty screen with no explanation reads as a bug to users, so treating empty as a designed state rather than an edge case is what makes a screen feel finished.

## 💡 What You'll Gain

By the end of today, you will handle every networking outcome — loading, success, empty, and error with retry — using an explicit state machine per screen.

## 📚 Dictionary for Developers

*   **Load State:** An enum modeling the phases of an async data load.
*   **State Machine:** A design where the UI is a function of an explicit finite state.
*   **`ContentUnavailableView`:** A built-in view for empty or unavailable states.
*   **Retry:** Re-attempting a failed operation on user request.
*   **Empty State:** A designed screen shown when a successful load returns no data.
