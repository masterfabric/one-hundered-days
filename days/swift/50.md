# Day 50: Networking (I) - Error Handling & Loading States

## 📝 Today's Tasks

1.  **Model a Load State:** Use an enum (`idle`/`loading`/`loaded`/`failed`) for the screen's state.
2.  **Render Each State:** Switch on the state to show a spinner, content, or an error view.
3.  **Add Retry:** Offer a retry action on failure.
4.  **Show Empty States:** Handle the successful-but-empty case with `ContentUnavailableView`.

## 📖 Task Explanations

A robust networked screen is a state machine, not just a happy-path fetch. Modeling load state as an enum with `loading`, `loaded`, `failed`, and empty cases forces you to design every situation the user might see, and switching on it keeps the view logic clear. Offering a retry on failure and using `ContentUnavailableView` for empty results turns rough edges into polished, considerate UX. This pattern — explicit states plus a view per state — is the professional standard for any screen that loads data.

## 💡 What You'll Gain

You will handle every networking outcome — loading, success, empty, and error with retry — using an explicit state machine per screen.

## 📚 Dictionary for Developers

*   **Load State:** An enum modeling the phases of an async data load.
*   **State Machine:** A design where the UI is a function of an explicit finite state.
*   **`ContentUnavailableView`:** A built-in view for empty or unavailable states.
*   **Retry:** Re-attempting a failed operation on user request.
