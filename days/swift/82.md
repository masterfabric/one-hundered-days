# Day 82: Performance & Concurrency in Practice - SwiftUI Rendering Performance

## 📝 Today's Tasks

1.  **Minimize Body Recomputation:** Keep bodies cheap and state minimal and localized.
2.  **Use Stable Identity:** Give `ForEach` stable IDs to avoid needless rebuilds.
3.  **Adopt Lazy State Init:** Use lazy initialization for expensive `@Observable` state (requires iOS 26+).
4.  **Measure View Updates:** Diagnose excessive redraws.

## 📖 Task Explanations

SwiftUI redraws by recomputing view bodies, so performance means keeping bodies cheap and only recomputing what changed. Localizing state (so a change touches the smallest possible subtree), giving `ForEach` stable identities (so rows aren't rebuilt wholesale), and extracting subviews all reduce wasted work. iOS 26 adds lazy state initialization for `Observable` types, deferring expensive setup until needed. Understanding what triggers a body recomputation — and avoiding heavy work inside `body` — is the difference between a buttery-smooth list and a janky one, especially with large data sets.

## 💡 What You'll Gain

You will keep SwiftUI rendering fast by minimizing recomputation, using stable identity, and adopting lazy state initialization.

## 📚 Dictionary for Developers

*   **Body Recomputation:** SwiftUI re-evaluating a view's `body` after a change.
*   **Stable Identity:** Consistent IDs letting SwiftUI reuse views across updates.
*   **Lazy State Init:** Deferring expensive `@Observable` setup until first use (requires iOS 26+).
*   **Redraw:** Re-rendering a view in response to state change.
