# Day 83: Performance & Concurrency in Practice - Main Actor & Off-Main Work

## 📝 Today's Tasks

1.  **Keep UI on the Main Actor:** Ensure UI-facing state is `@MainActor`-isolated.
2.  **Move Heavy Work Off-Main:** Find one heavy operation running on the main thread in your own app and relocate it into a background task or actor, assigning the finished result back to main-actor state.
3.  **Verify the Fix in Instruments:** Record a Time Profiler trace before and after the move, and confirm the main thread no longer stalls.
4.  **Measure an Actor Hop:** Time a loop that crosses an actor boundary on every iteration, then batch the same work into a single hop and compare the two timings.

## 📖 Task Explanations

Start by making UI ownership explicit. Mark view models and any type holding UI-facing state `@MainActor`, so the compiler guarantees those properties are read and written on the main thread. SwiftUI's `View` protocol is already main-actor-isolated, so this mostly means being deliberate about the types your views own.

Then get the heavy work out, starting from a real instance in your own app. Decoding a large payload, resizing images, sorting thousands of items — none of that belongs on the main actor. Synchronous heavy work on the main thread — or worse, inside a `body` — is the classic cause of dropped frames, and it is usually one function rather than a diffuse problem. Move it into a `Task.detached`, a `nonisolated` async function, or a dedicated actor, then assign the finished result back to your main-actor state. The pattern is compute elsewhere, publish on main.

Then prove the fix rather than assuming it. Record a Time Profiler trace with the Instruments workflow from yesterday, exercise the same screen, and compare against the trace you took before the change: the main thread should now be idle while the heavy work runs. Measuring both sides is what separates a real improvement from a plausible-looking refactor, and it catches the case where you moved the work but still block on its result.

Finally, understand that hops aren't free. Every crossing of an isolation boundary is a suspension and a potential context switch, so a loop that awaits an actor a thousand times is slower than one call that does a thousand items' work inside the actor. Batch at the boundary: cross deliberately, with as much work per crossing as makes sense.

## 💡 What You'll Gain

By the end of today, you will keep the UI responsive by isolating UI work to the main actor and moving heavy computation off-main deliberately.

## 📚 Dictionary for Developers

*   **Main Actor:** The isolation domain for main-thread UI work.
*   **Off-Main Work:** Computation performed away from the main thread.
*   **Main-Thread Blocking:** Stalling the UI by doing heavy work on main.
*   **Actor Hop:** Crossing from one isolation domain to another.
*   **Batching:** Doing more work per actor crossing to reduce suspension overhead.
