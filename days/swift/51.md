# Day 51: Networking (II) & Architecture - API Client

## 📝 Today's Tasks

1.  **Design an API Client:** Build a reusable client that performs requests and decodes responses.
2.  **Define Endpoints:** Model endpoints (path, method, body) as values.
3.  **Centralize Errors:** Map all failures to a single app error type.
4.  **Inject the Session:** Accept a `URLSession` (or protocol) for testability.

## 📖 Task Explanations

Scattering `URLSession` calls across views doesn't scale. A dedicated API client centralizes request construction, execution, decoding, and error mapping behind a clean interface, and modeling endpoints as values keeps the client generic. Crucially, injecting the session (ideally behind a protocol) lets you swap in a fake during tests. This is your first real architectural boundary: views and view models ask the client for data and never touch networking details directly, which keeps the codebase organized as it grows.

## 💡 What You'll Gain

You will build a reusable, testable API client that centralizes networking behind a clean boundary — your first real architecture layer.

## 📚 Dictionary for Developers

*   **API Client:** A reusable component encapsulating network requests and decoding.
*   **Endpoint:** A value describing a specific API route and its parameters.
*   **Error Mapping:** Translating diverse failures into one app-level error type.
*   **Injection Point:** A dependency (like the session) supplied from outside for testability.
