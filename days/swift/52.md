# Day 52: Networking (II) & Architecture - Repository Pattern

## 📝 Today's Tasks

1.  **Define a Repository Protocol:** Declare the data operations a feature needs.
2.  **Implement with the API Client:** Back the repository with the network client.
3.  **Abstract the Source:** Hide whether data comes from network, cache, or disk.
4.  **Return Domain Models:** Map API DTOs to clean domain types.

## 📖 Task Explanations

The repository pattern puts a protocol between your features and their data sources. A `TaskRepository` protocol declares operations like `fetchTasks()`; a concrete implementation fulfills them using the API client (and later a cache or database). Because features depend on the protocol, not the implementation, you can swap sources, combine network and local storage transparently, and inject fakes for testing. Mapping raw API DTOs to clean domain models at this boundary keeps networking concerns from leaking into your UI. This is a cornerstone of maintainable architecture.

## 💡 What You'll Gain

You will abstract data access behind repositories, decoupling features from their sources and enabling caching, offline, and testing.

## 📚 Dictionary for Developers

*   **Repository:** An abstraction over data sources exposing domain operations.
*   **DTO:** A Data Transfer Object mirroring an API's raw shape.
*   **Domain Model:** A clean model your app uses, mapped from DTOs.
*   **Abstraction Boundary:** A protocol hiding implementation details behind an interface.
