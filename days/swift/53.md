# Day 53: Networking (II) & Architecture - MVVM with @Observable

## 📝 Today's Tasks

1.  **Create a View Model:** Build an `@Observable` view model owning a screen's state.
2.  **Move Logic Out of Views:** Keep the view dumb; put loading and formatting in the view model.
3.  **Isolate to the Main Actor:** Mark the view model `@MainActor` for safe UI updates.
4.  **Depend on Protocols:** Have the view model depend on a repository protocol.

## 📖 Task Explanations

Create an `@Observable final class` that owns one screen's state: its data, its load state, and any derived values the view displays. The view then reads properties and calls methods — nothing else. That's the contract, and keeping it strictly is what makes MVVM useful rather than ceremonial.

Move logic out of the view accordingly. Fetching, filtering, sorting, date and currency formatting, and validation all belong to the view model; the view holds only layout and the bindings that carry user intent back. A good test is whether you could describe the screen's behaviour by reading the view model alone — if the view still contains an `if` about business rules, it hasn't moved yet.

Mark the class `@MainActor`. All of its state feeds the UI, so isolating it to the main actor means updates land on the right thread by construction and the compiler enforces it. Inside an async method, `await` the repository and then assign to properties directly — you're already back on the main actor when the call returns, so no manual dispatch is needed.

Finally, depend on a protocol, never a concrete repository. Take it in the initializer so production passes the real implementation and tests pass a fake that returns fixed data or throws on demand. That one decision is what makes a view model testable in isolation, and it's why Days 51 to 54 build toward each other rather than being separate topics.

## 💡 What You'll Gain

By the end of today, you will structure screens with `@Observable` view models, moving logic out of views and depending on protocols for testability.

## 📚 Dictionary for Developers

*   **MVVM:** An architecture separating Model, View, and ViewModel responsibilities.
*   **View Model:** An observable object holding a screen's state and logic.
*   **Thin View:** A view that only presents state and forwards user intent.
*   **`@MainActor` Isolation:** Ensuring a view model's UI-facing state updates on the main thread.
*   **User Intent:** An action the view forwards to the view model rather than handling itself.
