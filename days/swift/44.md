# Day 44: User Input & Forms - Validation

## 📝 Today's Tasks

1.  **Validate as You Type:** Derive validity from state and disable submit when invalid.
2.  **Show Inline Errors:** Display per-field messages for invalid input.
3.  **Validate on Submit:** Run full validation before accepting a form.
4.  **Model Validation Cleanly:** Keep validation logic in the model/view model, not the view.

## 📖 Task Explanations

The cleanest way to validate is to derive it, not store it. Add a computed property such as `var isValid: Bool { !name.isEmpty && email.contains("@") }` and drive the submit button with `.disabled(!isValid)`. Because it's computed from the same state the fields write to, it re-evaluates on every keystroke automatically — there is no separate validation flag to keep in sync, and therefore no way for it to go stale.

Inline errors work the same way: compute the message per field and show it beneath the row when the field is non-empty and invalid. The condition matters — validating a field the user hasn't touched yet turns a blank form into a wall of red. Style the message with `.font(.caption).foregroundStyle(.red)` and consider `.accessibilityLabel` so screen-reader users get the same signal.

Live feedback isn't enough on its own, so run a full check when the user submits. This is where you catch cross-field rules ("end date must be after start date"), trim whitespace, and handle anything you deliberately skipped while typing. On failure, set focus to the first offending field using yesterday's `@FocusState` rather than only showing a message — it saves the user hunting for the problem.

Where the rules live decides how testable they are. Keep them in your model or `@Observable` view model as ordinary Swift functions and properties, and let the view only display the result. Rules written that way can be unit-tested without a UI at all, reused on another screen, and reasoned about in isolation — which is exactly the split you'll formalise when you get to MVVM and testing.

## 💡 What You'll Gain

By the end of today, you will validate user input reactively and keep validation logic testable, preventing bad data while guiding users to correct it.

## 📚 Dictionary for Developers

*   **Validation:** Checking that input meets required rules before acceptance.
*   **Derived Validity:** Computing a form's submittable state from its inputs.
*   **Inline Error:** A message shown next to the field that failed validation.
*   **Separation of Concerns:** Keeping validation logic out of the view layer.
*   **Computed Property:** A property calculated on access, so it can never hold stale state.
*   **Cross-Field Rule:** A constraint involving more than one input, checked on submit.
