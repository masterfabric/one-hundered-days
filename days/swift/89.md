# Day 89: Navigation & Deep Linking - Coordinators & Routing

## 📝 Today's Tasks

1.  **Centralize Routing:** Introduce a router/coordinator owning the navigation path.
2.  **Decouple Screens:** Let screens request navigation without knowing destinations.
3.  **Model Routes as Values:** Define an enum of routes for the app.
4.  **Test Navigation Logic:** Unit-test routing decisions in isolation.

## 📖 Task Explanations

Introduce an `@Observable` router that owns the navigation path and inject it through the environment. Everything that navigates now goes through one object, so navigation stops being scattered across dozens of views and becomes a thing you can point at.

Expose intent, not destinations. The router's API should read `showDetail(for: item)` or `startCheckout()`, so a screen says what the user wants and the router decides which view answers that. The calling screen no longer imports or knows about the destination, which is what breaks the web of interdependencies that makes large SwiftUI apps hard to change.

Model routes as an enum — `case detail(Item.ID)`, `case settings`, `case checkout` — and the app's destinations become explicit and exhaustive. The compiler then tells you every place that needs updating when you add one, and the `navigationDestination` switch is a complete map of where the app can go.

Finally, test it. Because the router is a plain object with no UI, you can construct it, call `showDetail`, and assert on the resulting path — no view hierarchy, no UI test. Conditional routing especially ("if signed out, go to login instead") is exactly the logic that deserves a unit test, and it's untestable when it's an `if` inside a view.

## 💡 What You'll Gain

By the end of today, you will centralize navigation in a testable router, decoupling screens from destinations and keeping complex navigation coherent.

## 📚 Dictionary for Developers

*   **Coordinator/Router:** An object owning and directing navigation flow.
*   **Route:** A value representing a navigable destination.
*   **Decoupling:** Separating a screen from knowledge of where it navigates.
*   **Navigation Logic:** The rules deciding what to show next, testable in isolation.
*   **Intent-Based API:** Methods named for what the user wants rather than which screen appears.
