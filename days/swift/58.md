# Day 58: Persistence with SwiftData - Relationships

## 📝 Today's Tasks

1.  **Model a Relationship:** Link models with a `@Relationship` (one-to-many).
2.  **Set Delete Rules:** Choose cascade vs nullify delete behavior.
3.  **Traverse Related Data:** Read and mutate related objects through the graph.
4.  **Declare Inverse Relationships:** Add explicit inverses to both sides of a link and delete a parent to check the graph stays consistent.

## 📖 Task Explanations

Model a one-to-many link first: a `TodoList` with `var items: [Todo]` and a `Todo` with `var list: TodoList?`. SwiftData infers the relationship from the property types, so this alone works — the `@Relationship` macro is what you add when you need to configure the behaviour.

Delete rules are the main thing to configure. `@Relationship(deleteRule: .cascade)` on the parent's collection deletes the children with it, which is right when the children can't exist alone; `.nullify` (the default) just breaks the link and leaves them. Choose deliberately: cascade on data that should have been kept is unrecoverable, and nullify on data that shouldn't exist alone leaves orphans accumulating silently.

Traversal is ordinary property access. `list.items.count`, `todo.list?.name`, `list.items.append(todo)` — all of it reads like plain Swift, with SwiftData faulting related objects in as you touch them. Because of that laziness, a loop that walks a large graph can quietly perform a great many small fetches, which is worth remembering when a screen feels slow.

Finally, declare inverses explicitly with `@Relationship(inverse: \Todo.list)` on one side. That tells SwiftData the two properties are the same link seen from both ends, so appending to `list.items` also sets `todo.list` automatically. Delete a parent and check the children behaved as your delete rule promised — this is exactly the kind of thing that looks fine until real data accumulates.

## 💡 What You'll Gain

By the end of today, you will model connected data with SwiftData relationships and delete rules, building a correct, consistent object graph.

## 📚 Dictionary for Developers

*   **Relationship:** A modeled link between two persistent types.
*   **Delete Rule:** Behavior (cascade/nullify) applied to related objects on delete.
*   **Inverse Relationship:** The back-reference keeping both sides of a link in sync.
*   **Object Graph:** The connected network of related model instances.
*   **`@Relationship`:** The macro configuring delete rules and inverses on a linked property.
