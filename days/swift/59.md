# Day 59: Persistence with SwiftData - Migrations & Schema

## 📝 Today's Tasks

1.  **Version the Schema:** Define versioned schemas for your models.
2.  **Write a Migration Plan:** Provide a `SchemaMigrationPlan` for lightweight/custom migrations.
3.  **Handle Data Evolution:** Add, rename, or transform properties across versions.
4.  **Test the Upgrade Path:** Verify existing data survives a schema change.

## 📖 Task Explanations

Version your schema before you need to. Wrap your models in a `VersionedSchema` with an explicit version number, so `SchemaV1` is a named snapshot rather than an implicit "whatever shipped". Doing this on day one costs nothing; doing it after users have data is considerably harder.

Then write a `SchemaMigrationPlan` listing your schemas in order and the stages between them. A `.lightweight` stage covers changes SwiftData can infer on its own — adding an optional property, adding a new model, deleting one. A `.custom` stage runs your own code before or after the change, which is what renames and data transformations require.

Work through the three kinds of evolution. Adding an optional property is free. Adding a required one needs a default so existing rows have a value. Renaming or splitting a property needs a custom stage that reads the old shape and writes the new one — and remember every user upgrades from whichever version they had, so the chain of migrations must work end to end, not just from the latest.

Finally, test the upgrade path with realistic data, because this is where the real risk sits. Install the previous build, create a decent amount of content, then install the new one over it and confirm everything survived. A broken migration corrupts data on devices you'll never see, with no way to roll back — which is why testing it is a non-negotiable habit rather than an optional extra.

## 💡 What You'll Gain

By the end of today, you will evolve a SwiftData schema safely with versioning and migrations, protecting users' existing data across app updates.

## 📚 Dictionary for Developers

*   **Schema:** The definition of your persistent model structure.
*   **Migration:** The process of moving stored data to a new schema version.
*   **Lightweight Migration:** An automatic migration for simple, inferable changes.
*   **`SchemaMigrationPlan`:** The declaration of how to migrate between schema versions.
*   **`VersionedSchema`:** A named snapshot of your model structure at one point in time.
*   **Custom Migration Stage:** A migration step running your own code around a schema change.
