# Day 76: UI Testing & Accessibility - XCUITest

## 📝 Today's Tasks

1.  **Record a UI Test:** Create an `XCUITest` that launches and drives the app.
2.  **Query Elements:** Find views by accessibility identifier.
3.  **Assert UI State:** Verify labels, existence, and enabled state.
4.  **Handle Async UI:** Wait for elements with expectations.

## 📖 Task Explanations

UI tests exercise your app the way a user does — launching it, tapping, typing, and asserting what appears. `XCUITest` drives the real UI and finds elements by their accessibility identifiers, which is why setting stable identifiers on key views matters. You assert that labels are correct, buttons are enabled, and screens navigate as expected, using waits/expectations to handle asynchronous updates. UI tests are slower and more fragile than unit tests, so you use them sparingly for critical end-to-end flows (login, checkout) rather than every detail.

## 💡 What You'll Gain

You will write end-to-end UI tests with XCUITest for your app's critical flows, driving the real interface and asserting its state.

## 📚 Dictionary for Developers

*   **XCUITest:** Apple's framework for automated UI testing.
*   **Accessibility Identifier:** A stable string used to locate a view in tests.
*   **Element Query:** Finding UI elements to interact with or assert on.
*   **Expectation:** A wait for an asynchronous UI condition to become true.
