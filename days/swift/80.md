# Day 80: UI Testing & Accessibility - Review & Practice: Test Strategy

## 📝 Today's Tasks

1.  **Review the Section:** Re-run and repair your work from Days 76–79 — the XCUITest flow, VoiceOver labels, Dynamic Type checks, and previews.
2.  **Map Your Pyramid:** Count your unit, integration, and UI tests, and write down the ratio you're aiming for.
3.  **Refactor for Testability:** Extract one hard-to-test dependency behind a protocol and inject it.
4.  **Practice Project — Write a Test Plan:** Produce a one-page plan naming what you always test, what you deliberately don't, and which suites run in CI.

## 📖 Task Explanations

Open the tests you wrote across this section and run them all. Anything that has gone red since you wrote it is the most useful thing on today's list — a UI test that broke because a label changed is telling you it was tied to implementation, and fixing it now is cheaper than fixing it during a release.

Next, count what you have. The testing pyramid prescribes many fast unit tests at the base, fewer integration tests in the middle, and a handful of slow UI tests at the top covering critical end-to-end flows. That shape maximises confidence per second of test time, so if your counts are inverted — a dozen UI tests and three unit tests — note it and plan which UI tests should be pushed down a level.

Then make one thing easier to test. Pick a type that reaches out to the network, the clock, or the file system, define a protocol for what it actually provides, and inject it. Once the dependency arrives from outside, a test can pass a fake and assert on the outcome without waiting on a real request — and this is why architecture and testing keep reinforcing each other.

Finish with the plan, in writing. Name the code that always gets a test (business logic, money paths, tricky edge cases), the code that doesn't (trivial getters, generated boilerplate), and which suites run on every commit versus nightly. A test strategy that lives only in your head silently drifts toward either paranoia or neglect; one page keeps it honest, and it's what you'll extend when the CI/CD section arrives.

## 💡 What You'll Gain

By the end of today, you will have consolidated the testing and accessibility section and designed a balanced test strategy that invests effort where it yields the most confidence.

## 📚 Dictionary for Developers

*   **Testing Pyramid:** A model favoring many unit, some integration, few UI tests.
*   **Integration Test:** A test exercising several components together.
*   **Testability:** How easily code can be tested, driven by its design.
*   **Test Strategy:** A deliberate plan for what and how to test.
*   **Protocol Boundary:** An interface introduced so a real dependency can be swapped for a fake.
*   **Flaky Test:** A test that passes and fails without any code change.
